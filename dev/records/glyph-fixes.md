## Invisible UI glyphs, the guidance that produced them, and the gate (glyph-fixes)

### What was wrong

Blish HUD 1.3.0 exposes exactly one text face to modules. `ContentService.FontFace`
has a single member, Menomonia, and its 28 size/style variants carry a
byte-identical glyph table of **226 codepoints**: ASCII, Latin-1, and about
thirty punctuation marks. No geometric shape exists anywhere in it. NewKrytan
is a 183-glyph subset and is not reachable through `FontFace`; Consolas is a
`SpriteFont`, which `Label.Font` cannot take.

MonoGame.Extended's `BitmapFont.GetCharacterRegion` returns `null` for an
unknown codepoint, `DrawString` guards the blit on that region, and the pen
advance and `MeasureString` sit inside the same guard. So a codepoint the font
lacks renders as **nothing** and consumes **zero width**. The row stays
perfectly aligned, every layout assertion still passes, and a screenshot diff
sees an unchanged frame. That is why five of them shipped.

Plan History carried two:

- `Views/PlanHistoryTabContent.cs` pin toggle, `U+25CF` / `U+25CB`. The serious
  one: that glyph was the entire pinned-state model, so a pinned row and an
  unpinned row were indistinguishable to the player.
- the same file's delete button, `U+2715`.

`Views/RankerTabContent.cs` carries three more (`U+25B2`, `U+25BC`, `U+2715`),
fixed on its own branch.

### What replaced them

**Delete: `U+00D7` MULTIPLICATION SIGN**, which is in the font. A texture was
the first choice - Blish's `ref.dat` ships a matched 16px X pair at
`common/733269.png` and `common/733270.png` - and it was rejected on measured
grounds. `StandardButton.Paint` blits `Icon` untinted and forces
`_textColor = Color.Black` every frame, because its own art is light: the
`common/button-states` page samples ~(200,193,175). Both X textures are white
(~253,253,253 over their opaque pixels). Putting either inside the button
reproduces the invisible-affordance bug in a new medium. `StandardButton` also
places an icon-only button's icon 4px left of centre by construction
(`x = Width/2 + 8 - iconWidth - 4`), independent of width.

**Pin: a Blish `Checkbox` labelled "Pin".** The state now has real art -
`checkbox/cb-checked` versus `cb-unchecked` from Blish's own atlas, drawn from
local content with no network round trip - plus a word next to it, so pinned
and unpinned are unmistakable without hovering. It is the module's established
control for a boolean (`LogTabContent`'s Follow, `MainView`'s source filters),
and it is a state rather than an action, which is what the pin is.
`Checkbox` centres its 32px state art on `Height/2`, so handing it
`UiMetrics.ButtonHeight` seats it on the line the buttons beside it use.

The pin band widens from `IconButtonWidth` 28 to a new
`PlanHistoryRowLayout.PinToggleWidth` 44: `Checkbox` paints `20 + label width`,
and "Pin" measures 17px in the 14px face it draws with (summed `xAdvance` with
Blish's `LetterSpacing = -1`, read out of `menomonia-14-regular.xnb`).

### The guidance that caused it

`CLAUDE.md` told authors to represent runtime glyphs with escapes and offered
`"\u25BC"` and `"\u25B6"` as the examples. Both are absent from the font. The
escaping advice was right; the examples actively produced the defect. The rule
now says escaping a codepoint does not make it render, names the classes that
are absent wholesale, lists the useful present ones, and points at the
generated set and the CI step.

### The gate

`docs/font-codepoints.txt` is generated by `tools/dump-font-codepoints.py`,
which parses the glyph table out of every Menomonia XNB under Blish's
`Content/fonts/menomonia` and intersects them. Generated rather than
hand-maintained, so it is re-derivable when Blish updates its fonts rather
than a list somebody has to remember to edit.

The "UI glyph escapes exist in the shipped font" step in
`.github/workflows/tests.yml` reads that file and fails on any `\uXXXX` or
`\UXXXXXXXX` in module source that is not in it. Scope is deliberate: module
sources only, since tests and tools carry deliberately odd text and `ref/` is
API and wiki data rather than authored strings; whole-line comments are
skipped, so a comment may still name an absent codepoint in order to warn
about it. It sits directly after the ASCII-only step it depends on - that step
is what forces non-ASCII into escapes in the first place, which is what makes
a byte-level grep sufficient here.

`Views/RankerTabContent.cs`'s three are waived in the step so this change and
the Ranker branch do not collide. The waiver list is checked for staleness: a
waived pair that no longer appears in the source fails the step, so the
entries cannot outlive the fix.

Demonstrated on this tree: passes clean (285 module sources, 226 codepoints);
trips on a probe file whose string literal holds `\u2713` while the comment
naming the same codepoint on the line above does not trip it, and while a
line of `\u00D7 \u2014 \u2022` stays clean; passes again once the probe is
removed; and fails with "delete them from this step" when a waiver is made
stale.

### Closed and carried forward

- **Closed.** `Views/Rendering/SummarySectionRenderer.cs:774` records that a
  `U+2713` check-mark pill was considered and deferred because no live session
  was available to verify it. `U+2713` is not in the font. The "OK" pill was
  the correct call and the question is settled; the comment there still frames
  it as open, and belongs to the concurrent total-cost band branch to update.
- The sort indicators (`^` ascending, `v` descending) do render, but they are
  a diacritic and a lowercase letter: 3px of baseline and 4px of height apart,
  so they do not read as a matched pair. There is no symmetric up/down pair in
  the 226. Fixing that properly means shipping a small glyph atlas, which is
  out of scope here.
